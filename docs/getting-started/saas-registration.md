# SaaS Registration and SMTP

## Tenant model

One customer tenant equals one Company Group. A verified customer registration
creates, in one PostgreSQL transaction:

1. the Company Group;
2. its first Company;
3. the owner User with a server-generated username;
4. an `ORGANIZATION_OWNER` assignment at `COMPANY_GROUP` scope; and
5. an in-progress organization-onboarding record; and
6. the consumed verification challenge and security event.

No Company Group, Company or User exists before OTP verification. Provisioning
failure rolls back the transaction. A successful verification creates the
normal authenticated session and redirects the browser to `/onboarding`.

Platform Super Administrator is not a customer role. The first one is created
as a controlled deployment/operations action and is never exposed through a
public browser form. Existing Platform Super Administrators can manage later
administrative access from the authenticated Security area.

## Public API flow

The login page calls `GET /auth/capabilities` and displays only enabled flows.

Customer registration:

1. `POST /auth/register-organization`
2. `POST /auth/registration/verify`
3. `POST /auth/registration/resend` when required

Public forms never accept a role, scope, Company Group, Company or Branch ID.
Codes and usernames are generated by the backend.

## Organization onboarding

After email verification the Organization Owner completes:

1. Company Group name and description;
2. legal Company details;
3. the first Branch and address;
4. at least one Department, with optional first Designation and Shift;
5. a team-access explanation; and
6. a final review.

The owner cannot enter the main ERP until the required Company, Branch and
Department exist. All internal codes are generated by the backend and are not
editable in forms. Existing tenants are marked complete by the additive
onboarding migration, so their current workflow is unchanged.

## OTP safeguards

- Codes contain exactly six cryptographically generated digits.
- PostgreSQL stores only a secret-keyed HMAC, never the code.
- Default expiry is 10 minutes.
- Default maximum is five failed attempts.
- Default resend cooldown is 60 seconds.
- Resending overwrites the hash, invalidating the previous code.
- Conditional database updates allow only one concurrent verification to
  consume a challenge.
- Redis adds start, verify and resend rate limits. PostgreSQL expiry, attempt
  and cooldown controls remain authoritative if Redis is unavailable.
- SMTP secrets, codes, email bodies and development codes are redacted from
  application logs.

If SMTP delivery fails, the pending challenge remains and the API returns its
registration ID with `deliveryStatus=FAILED`. The OTP screen allows a safe
resend after the cooldown.

## SMTP production checklist

Use the SMTP values supplied by the deployment's mail provider:

```text
SMTP_HOST=<SMTP host>
SMTP_PORT=587
SMTP_USERNAME=<SMTP username>
SMTP_PASSWORD=<SMTP password or token>
SMTP_FROM_ADDRESS=noreply@your-verified-domain.example
SMTP_FROM_NAME=Group ERP
SMTP_REPLY_TO=
```

The transport uses STARTTLS with `secure=false`, `requireTLS=true`, minimum TLS
1.2, a 10-second connection timeout and a 30-second send timeout.
`SMTP_REPLY_TO` is optional.

Before setting `SAAS_SELF_REGISTRATION_ENABLED=true` in production:

- verify the sender domain with the SMTP provider;
- publish and verify the provider's required DNS records;
- configure the SMTP password or token;
- confirm a real OTP reaches the intended mailbox;
- keep `EMAIL_DEV_BYPASS=false`; and
- review and deploy the additive migration
  `20260729150000_organization_onboarding_and_generated_codes`.

Never run `prisma migrate reset` or `prisma migrate dev` against AWS RDS.
