# 00 — How to use this guide

This guide is for a **beginner** who wants to:

- create a new organization in the app
- understand **every button and field** on the way
- test the product as if it were their own company

You do not need to know HRMS, APIs, or databases. You only need the website running and a notepad.

---

## Before you click anything

1. Frontend is running at **http://localhost:3200**.
2. Backend is running at **http://localhost:4500**.
3. Open a notepad (not this git repo) and write:
   - owner email and password
   - company name
   - every employee email and password you create
4. Use **only the names you create**. Other companies may appear in dropdowns on a shared local database. Ignore them.

Health check (optional): open `http://localhost:4500/health/live`. You should see `"status":"ok"`.

## Words the app uses (learn these first)

| Word | Meaning in this app |
|------|---------------------|
| **Organization / Company Group** | The tenant you registered. One customer account. Example: Northstar Labs. |
| **Company** | A legal entity under that group. Example: Northstar Labs Pvt Ltd. You can have more than one company in a group. |
| **Branch** | An office / location. Attendance and leave use the branch **timezone**. Example: Kochi Head Office. |
| **Department** | A team inside a branch. Example: Human Resources, Engineering. |
| **Designation** | A job title. Leave policy rows and onboarding templates hang off this. Example: Staff, Team Lead. |
| **Shift** | A clock pattern (09:00–18:00). Needed before attendance can work. |
| **Employee** | The person in HR data (name, company, manager). **Not** a login by itself. |
| **User** | The login (email + password + roles). Must be **linked** to an Employee for My Workspace. |
| **Role** | What menus they can open (Owner, HR Manager, Employee, …). |
| **Scope** | *Where* that role applies (this company, this branch, or the whole group). |
| **Publish** | Make a draft live (calendar, work schedule, onboarding template). Drafts do not drive attendance or leave. |
| **My Workspace** | The employee’s daily home: punch, leave, calendar, onboarding. |

If you remember only one rule: **Employee is the person. User is the login. Link them.**

---

## Who does what (four practice people)

| Who | What they do in this guide |
|-----|----------------------------|
| **Organization Owner** (you, from register) | Create company structure, invite users, open admin menus |
| **HR Manager** | Calendars, employees, leave, onboarding, attendance review |
| **Manager** | Approve team leave / timesheets / some HR requests |
| **Employee** | My Workspace: punch, apply leave, see tasks |

Do **not** use the same person as Employee, Manager, and HR. Leave approval will look broken or confusing.

## Two tracks

- **Track 1 — Own company:** register → structure → people → calendar → attendance → leave. Enough to live in the app.
- **Track 2 — Full product:** add recruitment, onboarding checklists, assets, projects, finance, payroll.

Each chapter says **who** should be logged in.

## How each chapter is written

Every chapter uses the same shape:

1. **Why this exists**
2. **Who** clicks
3. **Where** (menu and URL)
4. **Screenshot** of the real page
5. **Field table** — every important option
6. **Do this** — numbered clicks with sample Northstar values
7. **Pass when**
8. **If it fails**
9. **Next**

Codes such as `COM-…`, `BR-…`, `EMP-…` are **generated by the app**. You type names. You do not invent codes.

## Screenshot note

Pictures in `images/` were taken from the local website. Some list pages show an existing practice tenant (names like ProdFix). **Your Northstar names will differ.** Trust the **field labels** and the **menu path**.

Some nested URLs 404 if you paste them in local Turbopack (for example Leave → Types, Recruitment → Openings, Attendance → Exceptions). **Always open them from the sidebar or an in-page button**, the same way a person uses the app. Shifts and Apply leave already open as a side panel (those screenshots are included).

Development-only banners (for example a verification code on screen) are hidden in the pictures. On a real customer environment the code arrives by email.

---

## Safety

- Never put passwords, OTP codes, or invitation links into git.
- Never test on a live customer company.
- If a button is visible, it should work **or** be disabled with a reason. If it looks clickable and fails silently, that is a product bug — stop and record the page URL.
