# Project Lite DB, API and UI Implementation Plan

## 1. Purpose and release boundary

This document is the implementation contract for Project Lite. It retains the original Project and Task journey while hardening the current Project scaffolding for production use.

The authoritative flow is:

`Project -> Stages/WBS -> Team -> Tasks -> Assignment -> Work/review -> Approved weekly timesheet -> Office Finance cash summary`

This is a plan, not evidence that migrations, APIs, UI, tests or UAT are complete.

### Locked product behavior

- Projects belong to one Company and may optionally be limited to one Branch.
- Project types are `CLIENT` or `INTERNAL`.
- Client Projects require an active same-Company Customer/Both Business Party; Internal Projects have no Business Party.
- Stages plus parent/child tasks provide the Lite WBS. A separate WBS engine is not created.
- A Project has one active Project Manager and multiple effective-dated team members.
- Tasks may have multiple active participants, but every participant must be an active Project team member.
- Assigned participants perform work; the Project Manager controls assignment, review, completion and cancellation.
- Employees submit weekly work logs. The reporting manager captured at submission approves or returns the whole week.
- Project Managers see approved time totals but do not approve individual work-log lines.
- Project Finance Summary uses only approved/reversed Office Finance transactions tagged to the Project and is labelled an operational cash result, not profitability.
- Project files use Secure File Storage; local `filePath` values are not a production document contract.
- CRM opportunity conversion, contracts, billing, invoices, variations, deliverables, risks, forecasts, Gantt planning, resource heatmaps, earned value and formal profitability are deferred.

## 2. Current baseline and dependencies

The repository already contains `Project`, `ProjectStage`, `ProjectTeamMember`, `ProjectTeamMemberHistory`, `ProjectTask`, `TaskParticipant`, `TaskSubmission`, `TaskReview`, `TaskAssignmentHistory`, `WorkLogHeader`, `WorkLogLine`, `WorkSchedule` and `TaskWorkSession`.

The current implementation is scaffolding:

- States, roles and several action values are free strings.
- `Project.projectCode` is globally unique instead of Company-scoped.
- Child records lack Company/Branch snapshots and use bare-ID relations.
- `projectmanagerId` is misspelled and legacy client data is stored as strings.
- Generic controllers expose unscoped list/direct-ID CRUD, arbitrary PATCH updates and hard deletes.
- Project Task validation does not enforce Company, team membership, actor authority, state, version or parent cycles.
- Two task-participant service paths can diverge.
- Work logs accept client-selected Employees, allow invalid line shapes/hours and use a generic approval path that can bypass reporting-manager checks.
- Task Work Session can create weekly headers without using a hardened timesheet transaction.
- `TaskSubmission.filePath` is a local-path contract.
- There are no Project pages or focused Project browser tests; navigation marks the module as planned.

Dependencies:

- [Office Finance Lite](./office-finance-lite-db-api-ui-implementation-plan.md) owns the shared `BusinessParty` and `CompanyFinancialProfile` migrations.
- Secure Project attachments require accepted Secure File Storage and Delivery V2.
- Project Lite may run before Office Finance transactions are enabled; in that case Finance Summary returns `enabled: false` and the UI hides its monetary cards.

### 3.2 Project aggregate

Harden `Project`:

| Field | Contract |
|---|---|
| `version` | Optimistic concurrency token. |
| `projectCode` | Generated by `NumberSeriesService`; unique within Company. |
| `projectType` | `CLIENT` or `INTERNAL`. |
| `businessPartyId` | Required only for Client Projects. |
| `branchId` | Optional Project operating Branch. |
| `projectManagerId` | Required before activation; active same-Company Employee. |
| `currencyCode` | Company base-currency snapshot. |
| `expectedIncome`, `expenseBudget` | Optional `Decimal(18,2)` Draft estimates. |
| lifecycle actors/timestamps | Activation, hold, completion, cancellation and archive evidence. |

Keep the physical legacy `projectmanagerId` column mapped to the correctly named Prisma/API field with `@map("projectmanagerId")` during compatibility, unless the migration safely renames it. Never expose the typo in public DTOs.

Rules:

- Unique `(companyId, projectCode)`; remove global code uniqueness only after duplicate preflight.
- Client Project: active `CUSTOMER`/`BOTH` Business Party in the same Company.
- Internal Project: `businessPartyId IS NULL`.
- Optional Branch and Project Manager use Company-qualified composite foreign keys.
- `startDate <= endDate` when an end date exists.
- Expected income and budget are non-negative and editable only while Draft.
- Activation requires manager, start date and at least one non-cancelled stage.
- Completion requires no active stage/task.
- No Project is hard-deleted. Draft with no history may be archived; otherwise lifecycle commands preserve it.
- Keep `clientName`, `clientContact`, `contractValue` and legacy `currency` as historical read-only fields until reconciliation proves they can be retired.

### 3.3 Stages and WBS tasks

Harden `ProjectStage`:

- Add `companyId`, `version`, typed status and lifecycle actors/timestamps.
- Unique `(projectId, stageCode)` and `(projectId, sequenceNo)`.
- Company-qualified relation to Project; all historical references use `Restrict`.
- Stage dates must fall within Project dates when Project boundaries exist.
- A stage with tasks cannot be hard-deleted.

Harden `ProjectTask`:

- Add `companyId`, `version`, typed status, cancellation/review evidence and archive metadata.
- Retain `projectId`, `stageId`, optional `parentTaskId`, code/name, priority, planned/review hours, progress and dates.
- Unique `(projectId, taskCode)`; Stage and parent must belong to the same Company and Project.
- Reject self-parenting and parent cycles. Use a transaction lock plus recursive ancestor check for commands and a database trigger as direct-SQL backstop.
- A parent can contain sub-tasks at any Lite depth; no separate WBS entity is added.
- `completionPercentage` is server-maintained: `0` before work, an allowed intermediate value while active, and exactly `100` when completed.
- Task date range must be valid and remain within Stage/Project boundaries where configured.
- A task with participant, transition, work-log or attachment history cannot be hard-deleted.

### 3.4 Team and task assignment

Harden `ProjectTeamMember`:

- Add `companyId`, `version`, typed status, assigned/ended actor User IDs and timestamps.
- Keep role, allocation percentage, start/end dates and remarks as immutable history where applicable.
- Require `0 < allocationPercentage <= 100`.
- Employee must be active and belong to the same Company. Same-Company cross-Branch membership is allowed.
- Partial unique index permits one active membership per `(projectId, employeeId)`.
- Ending membership is rejected while the Employee has an active task assignment; tasks must be reassigned or cancelled first.
- Update `ProjectTeamMemberHistory` to use actor User IDs, Company snapshot, operation ID and protected reason. Do not derive `changedBy` from the affected Employee.

Harden `TaskParticipant` as the single authoritative assignment model:

- Add `companyId`, `projectId`, `version`, typed status and assignment/end evidence.
- Employee must have an active membership in the same Project.
- Partial unique active assignment per `(taskId, employeeId, role)`.
- Planned/actual hours are non-negative decimals; actual hours are derived from approved Project work-log lines, not freely edited.
- Ending/reassigning a participant writes `TaskAssignmentHistory` and a domain action event.

Choose one task-participant service as authoritative. The other existing service/controller must delegate to it or be unregistered; two independent mutation paths cannot remain live.

### 3.5 Task submission and secure files

Add `PROJECT_SUPPORTING` to `FileUploadPurpose` and `PROJECT_RECORD` to `FileRetentionClass`.

Add `ProjectDocument`:

- `companyId`, `projectId`, optional `taskId`, optional `taskSubmissionId`.
- `fileObjectId`, document purpose/title, uploader and timestamp.
- Unique `(companyId, fileObjectId)` for one authoritative Project link.
- Company-qualified `Restrict` relations and a same-Project shape constraint.
- Only a same-Company `CLEAN` FileObject can be linked or downloaded.

Replace public use of `TaskSubmission.filePath` with secure ProjectDocument/FileObject references. Existing paths remain historical strings and are not downloadable until imported and reconciled into File Storage.

Harden `TaskSubmission`/`TaskReview` with Company/Project snapshots, versions, typed decisions/statuses, actor User/Employee evidence and immutable submission versions. A task can have multiple submission rounds, but only its active participant can submit and only the Project Manager can return/complete it.

### 3.6 Weekly timesheets

Harden `WorkLogHeader`:

- Add `companyId`, `branchId`, `employeeId`, `version` and typed status.
- Store date-only `periodStart`/`periodEnd`; Lite uses a Company-configured weekly boundary and Branch timezone.
- Snapshot reporting-manager Employee/User at submission.
- Add submitted, approved, returned and cancelled actor/timestamp/reason evidence.
- Unique `(companyId, employeeId, periodStart)`; period end must match the configured week.
- `totalHours` is derived from lines using decimal arithmetic.

Harden `WorkLogLine`:

- Add `companyId`, `branchId`, `employeeId` and `version` snapshots.
- Exactly one of `taskId` or `workCategoryId` is present.
- `0 < hours <= 24`, work date lies inside the header period, and total employee hours across every line for a business date cannot exceed 24.
- A Project-task line requires an active assignment for that Employee on that date and a non-cancelled Project/task.
- Non-Project category must be active and same Company.
- Lines are mutable only while the header is Draft or Returned.

Submission snapshots the current active reporting manager. If no manager with an active User exists, return `TIMESHEET_APPROVER_NOT_CONFIGURED`; do not search by designation name or choose an arbitrary role holder.

The generic Approval service must reject/delegate `WORK_LOG_HEADER`. Only the dedicated scoped Timesheet service may approve or return it. Task Work Session may contribute draft lines only by calling the same transaction-aware WorkLog service; it cannot create or mutate submitted headers independently.

### 3.7 Events and idempotency

Add `ProjectActionEvent` as append-only evidence for Project, stage, membership, assignment, task, review, timesheet and document actions. Store Company, entity type/ID, from/to state, actor, version before/after, operation ID, timestamp and protected reason/note.

Add `ProjectCommandReceipt`:

- Unique `(companyId, operationId)`.
- Command type, actor, canonical-request HMAC key/format versions, result ID and safe response snapshot.
- Same command/payload replays the result; conflicting reuse returns `OPERATION_ID_REUSED`.
- Safe snapshots exclude private document metadata and free-text evidence.

### 3.8 Required indexes and backstops

Indexes:

- Project Company/status/manager/Branch lists.
- Active team membership and employee Project list.
- Tasks by Project/Stage/status/due date and participant personal queue.
- Submitted timesheets by approver/status/date.
- Work-log Employee/date and Project summary aggregation.
- Project documents and action history.

Database checks/triggers enforce tenant-qualified relations, typed state/evidence shapes, Project/Stage/task date rules, parent cycles, active membership assignment, daily hour ceiling, terminal immutability and no hard deletion of historical records.

## 4. Feature gate, permissions and API conventions

### 4.1 Feature control

- `PROJECTS_LITE_ENABLED=false` by default.
- `PROJECTS_LITE_COMPANY_IDS` is the server-side Company allowlist.

Every list, direct ID, mutation, notification job and Project attachment checks the resolved Company. Company Group context must select one Company. Frontend navigation consumes authenticated module capabilities rather than public environment variables.

### 4.2 Permissions and record authority

- `projects.projects.read`: scoped Project monitoring.
- `projects.projects.manage`: Project lifecycle, stage, team and task management.
- `projects.tasks.work`: work on tasks assigned to the authenticated Employee.
- `projects.timesheets.submit`: maintain and submit own weekly timesheets.
- `projects.timesheets.approve`: view and decide only timesheets assigned to the authenticated reporting manager.

Map Project Manager role to read/manage and timesheet approval; Employee self-service receives task-work and timesheet-submit. Organization Owner may hold all permissions, but task assignment and reporting-manager record rules still apply.

Add route-policy entries for Project and team endpoints. Specific `/me/project-tasks`, `/me/timesheets` and `/team/timesheets` rules must precede the generic `/me` rule. Permission is necessary but never substitutes for Project-manager, assignee or reporting-manager identity checks.

### 4.3 Wire conventions

Use the global envelope and paged list shape:

```ts
type ApiResponse<T> = { success: true; data: T };
type Page<T> = { items: T[]; total: number; page: number; limit: number };
```

Use `keyword`, `sortBy`, `sortOrder`, `page`, `limit` and resource-specific sort allowlists. Decimal values are strings.

Create commands accept `operationId`; commands on existing resources accept `operationId`, `expectedVersion` and a reason where evidence is required. Company, actor Employee and Branch are derived from authenticated context or authoritative relations, never trusted from command bodies.

## 6. State machines and transactions

### 6.1 Project and task transitions

```text
Project: DRAFT -> ACTIVE -> ON_HOLD -> ACTIVE -> COMPLETED
         DRAFT/ACTIVE/ON_HOLD -> CANCELLED

Task:    OPEN -> ASSIGNED -> IN_PROGRESS -> WAITING_REVIEW -> COMPLETED
         WAITING_REVIEW -> IN_PROGRESS
         OPEN/ASSIGNED/IN_PROGRESS/WAITING_REVIEW -> CANCELLED
```

- Assigning the first participant changes `OPEN -> ASSIGNED`.
- Only an active participant may start or submit review.
- Only the Project Manager may return, complete or cancel a task.
- Completion sets progress to 100; cancellation does not count as completed work.
- Removing the last active participant from an unstarted task returns it to `OPEN`.
- Reassignment while in progress is direct, reasoned and audited; do not create an unassigned in-progress state.

### 6.2 Timesheet transition

```text
DRAFT -> SUBMITTED -> APPROVED
SUBMITTED -> RETURNED -> SUBMITTED
DRAFT/RETURNED -> CANCELLED
```

- Submit locks header/lines, validates daily totals and assignments, snapshots the reporting manager, then writes audit/outbox atomically.
- Only the snapshotted reporting manager can approve or return.
- The submitter cannot approve their own work log.
- Approved headers/lines are immutable. Corrections require a new documented correction workflow in a later release; they are not silently edited.

### 6.3 Concurrency and lock order

Commands use serializable transactions where multi-row invariants are involved, with bounded retry for serialization/deadlock errors.

Canonical lock order:

1. Project command receipt.
2. Company/feature and required permission records.
3. Project and Project Manager.
4. Stage/task hierarchy.
5. Team membership and task participants.
6. WorkLog header and lines when applicable.
7. FileObject when attaching.
8. Action evidence, audit and outbox.

Expected-version updates use `WHERE id = ? AND version = ?`, increment version once, and return `409 PROJECT_STATE_CHANGED`/`TASK_STATE_CHANGED` on zero affected rows.

- `/my-workspace/projects`.
- `/my-workspace/timesheets`.

Project detail tabs:

- Overview.
- Stages.
- Team.
- Tasks.
- Time.
- Finance Summary.

The existing `/projects/resources` planned item is removed or redirected because a resource heatmap/planning page is deferred.

UI rules:

- Render all buttons from server `allowedActions`.
- Project/team/task pickers consume server eligibility endpoints and never fetch an organization-wide Employee list to filter locally.
- My Workspace uses actor-scoped assigned-task and own-timesheet APIs.
- Manager Dashboard pending approvals use `/team/timesheets`, not generic approval records.
- Finance Summary shows `enabled: false` until Office Finance is available and never says Profit, Margin or Profitability.
- No optimistic lifecycle, assignment, review or approval transitions.
- Preserve reason/remarks on `409` and refetch authoritative state.
- Task documents upload to quarantine, wait for `CLEAN`, then link through the Project attachment API.
- Replace hard-coded Employee workspace Project count with the actor-scoped Project summary.

## 8. Notifications

Write safe outbox events in the same transaction for:

- Project activation/hold/completion/cancellation.
- Team member added/ended.
- Task assigned/reassigned, due soon, overdue, submitted, returned and completed.
- Timesheet submitted, returned and approved.

Resolve recipients using exact active RoleAssignment/Employee scope and actual Project/assignment/manager relationships. Use `INTERNAL_USER` delivery recipient type. Payloads contain safe IDs, codes, dates and status only; no free-text review notes or document metadata.

## 9. Migration and compatibility

Use new migrations after the latest applied migration; do not modify historical Project/Work Log migrations.

1. `project_lite_expand`: typed enums, new nullable snapshots/versions/evidence, receipts/events/documents, permissions and supporting unique keys.
2. `project_lite_reconcile`: reports and deterministic mapping/backfill.
3. `project_lite_contract`: type conversions, not-null/composite FKs, partial unique indexes, checks, triggers and final indexes.

Preflight must report:

- Duplicate Project codes within a Company.
- Unknown Project/Stage/Task/participant/work-log statuses.
- Cross-Company Branch, manager, member, task, category or work-log relationships.
- Missing/inactive manager or members.
- Duplicate stage code/sequence and task code/name conflicts.
- Parent self-links/cycles and cross-Project parent links.
- Invalid allocations, task progress, periods, line shapes or daily hours.
- Work logs with unsafe generic approval state.
- Local `TaskSubmission.filePath` values.
- Client strings that cannot be mapped unambiguously to an existing Business Party.

Deterministic status mapping:

- Project `DRAFT`, `PROPOSAL`, `APPROVED` -> `DRAFT`.
- Project `ACTIVE` -> `ACTIVE`.
- `ON_HOLD` variants -> `ON_HOLD`.
- `COMPLETED`, `CLOSED` -> `COMPLETED`.
- `CANCELLED` -> `CANCELLED`.
- Stage `OPEN` -> `PLANNED`; known active/completed/cancelled values map directly.
- Task `NOT_STARTED`/`OPEN` -> `OPEN`, known assigned/in-progress/review/completed/cancelled values map directly.

Infer legacy Project type as Client only when legacy client fields are present; copy `contractValue` to `expectedIncome` and currency only as a legacy snapshot. Do not invent or merge Business Parties by name. An operator supplies an explicit mapping for every legacy Client Project before V2 enablement. Unknown or ambiguous values stop contract migration.

Unsafe legacy controllers (`/project-stages`, `/project-team-members`, `/project-tasks`, `/task-participants`, `/task-submissions`, `/task-reviews`, `/work-log-header`, `/work-log-line` and generic WorkLog approvals) must either be unregistered at cutover or delegate to the same V2 scoped services. Feature enablement is prohibited while a bypass remains.

- Assignment/reassignment and member-end races.

Required non-mock browser personas:

1. Organization Owner sees the module only for an enabled Company.
2. Project Manager creates a Client/Internal Project, stages, team and tasks.
3. Assigned Employee starts work, submits review and logs time.
4. Another Employee cannot mutate the task.
5. Project Manager returns/completes task work.
6. Employee submits a weekly timesheet.
7. Correct reporting manager approves; wrong manager/self-approval is denied.
8. Project detail shows consistent time and narrow Office Finance totals.
9. Another Company cannot list/open/mutate records or files.

Production acceptance requires zero unsafe legacy-route bypasses, rehearsed from-zero and production-like migrations, catalog verification, lint/type-check/build/test evidence, real API/browser personas, secure-file and notification evidence, backup/restore rehearsal, monitoring and recorded technical/business sign-off.
